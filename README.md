# Система управления игровой библиотекой

Github - https://github.com/seffax098/gameLibrary

Приложение для учёта общей коллекции видеоигр: хранение списка игр, учёт пользователей, запись игровых сессий, личный прогресс прохождения каждого пользователя, поиск, сортировка и статистика библиотеки.

Консольная версия приложения (ПР3) дополнена веб-интерфейсом на Django (ПР5):
библиотеку, карточки игр с прогрессом игроков и историю игровых сессий
теперь можно просматривать в браузере.

## Используемые технологии

- Python 3.10+;
- Django 5.2 (LTS) — веб-фреймворк;
- HTML — разметка веб-страниц;
- CSS и Bootstrap 5.3 (подключается через CDN) — оформление страниц;
- JSON — хранение данных (на этапе перехода к Django ORM);
- pytest и `django.test` — автоматизированные тесты;
- flake8, mypy (с `django-stubs`) и pylint — проверка качества кода и типов.

## Назначение

Приложение предназначено для учёта и организации коллекции видеоигр, которой
пользуются один или несколько игроков: добавление игр в библиотеку, запись
игровых сессий, отслеживание личного статуса прохождения, сортировка и поиск
по различным критериям (жанр, платформа, год выхода и т.д.).

## Целевая аудитория

- Геймеры, ведущие учёт своей игровой коллекции;
- Семьи и небольшие клубы с общей библиотекой игр, где у каждого игрока свой прогресс;
- Пользователи, которым нужно отслеживать статус прохождения игр.

## Описание предметной области

Библиотека содержит игры с их характеристиками (жанр, платформа, год
выпуска, примерное время прохождения, оценка). Пользователи библиотеки
записывают игровые сессии: кто, во что, в какой день и сколько часов играл.
По сессиям для каждого пользователя вычисляется личный прогресс прохождения
каждой игры.

Правила предметной области:

- сессия всегда связана с существующим пользователем и существующей игрой;
- у пользователя может быть только **одна активная сессия по игре за день**;
  другой пользователь в тот же день может играть в ту же игру;
- отменённая сессия не удаляется, а остаётся в истории с пометкой
  «отменена»: она не учитывается в прогрессе и не занимает день;
- прогресс личный: если двое игроков прошли игру наполовину, игра не
  считается пройденной ни одним из них;
- при удалении игры удаляются и её сессии;
- адрес электронной почты пользователя уникален.

## Объектная модель

Основные сущности предметной области представлены классами пакета `models`.

| Класс | Атрибуты | Основное поведение |
|---|---|---|
| `Game` | `id`, `title`, `genre`, `platform`, `release_year`, `hours_total`, `rating` | проверка данных, поиск по запросу, возраст и эпоха игры, описание оценки, строковое представление |
| `User` | `id`, `name`, `email` | проверка имени и почты, поиск по запросу, создание из данных, строковое представление |
| `GameSession` | `id`, `user`, `game`, `date`, `hours`, `is_cancelled` | отмена, проверка занятости дня, строковое представление с учётом состояния |
| `Progress` | `user`, `game`, `hours` | процент, статус, шкала и оставшееся время прохождения, строковое представление |

### Game — игра

Объект `Game` представляет игру библиотеки. Конструктор проверяет данные,
поэтому объект всегда корректен: при пустом названии, неизвестной платформе,
неверном годе, неположительном времени прохождения или оценке вне 0–10
возбуждается `ValueError`.

Атрибуты:

- `id` — уникальный идентификатор игры;
- `title` — название;
- `genre` — жанр (пустой заменяется на «Не указан»);
- `platform` — платформа из списка `PLATFORMS`;
- `release_year` — год выпуска;
- `hours_total` — примерное время прохождения в часах;
- `rating` — оценка от 0 до 10 (0 — не выставлена).

Методы:

- `__init__()` — создание игры с проверкой данных;
- `__str__()` — строковое представление: `Hades (Nintendo Switch, 2020)`;
- `matches(query)` — подходит ли игра под поисковый запрос по названию или жанру;
- `is_released_since(year)` — выпущена ли игра не раньше указанного года;
- `age()` — возраст игры в годах;
- `era()` — «новинка», «современная игра» или «классика»;
- `rating_label()` — текстовое описание оценки;
- `validate_platform()`, `validate_year()`, `validate_rating()` — проверки данных (`@staticmethod`);
- `from_data(data)` — создание игры из данных JSON (`@classmethod`);
- `to_data()` — данные игры для сохранения в JSON.

### User — пользователь

Объект `User` представляет пользователя системы — игрока, который записывает
игровые сессии.

Атрибуты:

- `id` — уникальный идентификатор пользователя;
- `name` — имя пользователя;
- `email` — адрес электронной почты (хранится в нижнем регистре).

Методы:

- `__init__()` — создание пользователя с проверкой имени и почты;
- `__str__()` — строковое представление: `Иван Петров <ivan@example.com>`;
- `matches(query)` — подходит ли пользователь под запрос по имени или почте;
- `validate_email()` — проверка формата адреса почты (`@staticmethod`);
- `from_data(data)` — создание пользователя из данных JSON (`@classmethod`);
- `to_data()` — данные пользователя для сохранения в JSON.

### GameSession — игровая сессия

Объект `GameSession` описывает, сколько часов пользователь играл в игру в
определённый день. Сессия хранит **ссылки на объекты** `User` и `Game`, а не
их идентификаторы.

Атрибуты:

- `id` — уникальный идентификатор сессии;
- `user` — объект `User`;
- `game` — объект `Game`;
- `date` — дата сессии (`datetime.date`);
- `hours` — количество сыгранных часов (больше нуля);
- `is_cancelled` — признак отмены (свойство только для чтения).

Методы:

- `__init__()` — создание сессии, связанной с пользователем и игрой;
- `__str__()` — описание сессии, для отменённой добавляется «(отменена)»;
- `cancel()` — отмена сессии, повторная отмена вызывает `ValueError`;
- `occupies_day(user, game, date)` — занимает ли сессия день пользователя по игре;
- `from_data(data, user, game)` — создание сессии из данных JSON и найденных объектов (`@classmethod`);
- `to_data()` — данные сессии для JSON, ссылки заменяются на `user_id` и `game_id`.

### Progress — прогресс прохождения

Объект `Progress` описывает прогресс конкретного пользователя в конкретной
игре. Он создаётся функцией `get_progress()` по часам активных сессий
пользователя. Процент, статус и шкала — вычисляемые свойства (`@property`):
они не хранятся, а рассчитываются по сыгранным часам и времени прохождения
игры.

Атрибуты: `user`, `game`, `hours`.

Свойства и методы:

- `percent` — процент прохождения, не больше 100;
- `status` — «Не начата», «В процессе» или «Пройдена»;
- `progress_bar` — текстовая шкала вида `[####------]`;
- `hours_left` — сколько часов осталось до примерного времени прохождения;
- `__str__()` — `[####------] 40% - В процессе`.

## Взаимодействие объектов

```text
User ──записывает──> GameSession ──относится к──> Game
  │                       │
  │                       ├── user ──> User
  │                       └── game ──> Game
  │
  └──────── Progress (user, game, hours) <── часы активных сессий
```

- `GameSession` связывает пользователя и игру (композиция): данные связанных
  объектов доступны напрямую — `session.user.name`, `session.game.hours_total`.
- `Progress` объединяет пользователя, игру и сумму часов его активных сессий.
- Запись сессии выполняет функция `log_session()`: она проверяет, свободен ли
  день (`is_day_free()` → `GameSession.occupies_day()`), создаёт объект
  `GameSession` и добавляет его в коллекцию. Если день занят, возвращается
  `None`.
- Отмена выполняется функцией `cancel_session()`: она находит сессию и
  вызывает её метод `cancel()`; объект остаётся в коллекции.

Сценарий записи сессии в `main.py` (`create_new_session()`):

```text
Ввод ID пользователя → поиск User
        ↓
Ввод ID игры → поиск Game
        ↓
Ввод даты и часов
        ↓
log_session(): проверка дня → создание GameSession(user, game, ...)
        ↓                                  → добавление в коллекцию
Вывод сессии и нового прогресса пользователя
```

Коллекции приложения — списки объектов: `list[Game]`, `list[User]`,
`list[GameSession]`. Операции, относящиеся к одному объекту, реализованы
методами классов; операции над коллекциями (поиск, отбор, сортировка,
проверка дня, подсчёт часов) остались функциями модулей.

## Принципы ООП в проекте

- **Инкапсуляция.** Данные и поведение объединены в объектах. Конструкторы
  `Game` и `User` проверяют данные, поэтому некорректный объект создать
  нельзя. Состояние отмены сессии хранится в закрытом атрибуте
  `_is_cancelled`: снаружи оно доступно только для чтения через свойство
  `is_cancelled`, а изменить его можно только методом `cancel()`.
- **Композиция вместо наследования.** `GameSession` и `Progress` содержат
  объекты `User` и `Game`. Наследование в проекте не используется намеренно:
  между сущностями нет отношения «является» (сессия не является игрой или
  пользователем), а общий базовый класс только ради `id` не дал бы пользы.
- **Полиморфизм.** Все классы реализуют `__str__()`, поэтому любой объект
  выводится одинаково — `print(obj)` или f-строкой. Классы `Game`, `User` и
  `GameSession` поддерживают общий интерфейс `to_data()`, которым пользуется
  модуль `storage`.
- **Декораторы.** `@staticmethod` — проверки данных (`Game.validate_year()`,
  `User.validate_email()`), `@classmethod` — фабричные методы `from_data()`,
  `@property` — вычисляемые свойства `Progress` и `GameSession.is_cancelled`.

## Возможности

Игры:

- просмотр библиотеки и подробной карточки игры с прогрессом каждого игрока;
- поиск игр по подстроке названия или жанра;
- отбор игр по платформе;
- сортировка по названию, году выпуска, оценке и времени прохождения;
- добавление и удаление игр.

Пользователи:

- просмотр списка пользователей с их игровым временем;
- поиск пользователя по имени или адресу почты;
- профиль пользователя: статусы игр и личный прогресс;
- добавление пользователя.

Игровые сессии:

- запись сессии пользователя по игре с проверкой занятости дня;
- отмена сессии с сохранением её в истории;
- просмотр всех сессий, включая отменённые.

Сводка:

- статистика библиотеки: часы, средняя оценка, игры по платформам, самые
  популярные игры и самые активные игроки;
- справка по классам и функциям проекта, построенная средствами интроспекции;
- сохранение и загрузка данных в JSON-файлах.

Веб-интерфейс (ПР5):

- главная страница со сводкой библиотеки, популярными играми и самыми
  активными игроками;
- список игр и карточка игры: характеристики, эпоха, оценка, личный
  прогресс каждого игрока и активные сессии по игре;
- список игровых сессий (включая отменённые) и карточка сессии со
  связанными игрой и игроком и прогрессом игрока в этой игре;
- навигация между страницами, ответ с кодом 404 для несуществующих
  игр и сессий.

## Веб-интерфейс на Django

### Сценарии консольной версии в вебе

На ПР5 в веб-интерфейс перенесено **отображение** данных. Операции,
изменяющие данные, требуют форм и POST-запросов и остаются в консольной
версии до следующих работ.

| Сценарий консольной версии | Веб-интерфейс ПР5 |
|---|---|
| просмотр библиотеки и карточки игры с прогрессом игроков | страницы `/games/` и `/games/<id>/` |
| просмотр всех сессий, включая отменённые | страницы `/sessions/` и `/sessions/<id>/` |
| статистика библиотеки | главная страница `/` |
| добавление и удаление игр, поиск, отбор, сортировка | отложено — нужны формы |
| запись и отмена сессий | отложено — нужны формы и POST-запросы |
| добавление и поиск пользователей, профиль пользователя | отложено — появятся вместе с аутентификацией |

### Django-проект и приложения

Django-проект `gamelibrary` создан в корне репозитория
(`django-admin startproject gamelibrary .`), поэтому `manage.py` лежит
рядом с `main.py`, а код ПР3 не перемещался.

| Приложение | Область | Почему отдельное приложение |
|---|---|---|
| `homepage` | главная страница и общий каркас страниц | точка входа, не относится к играм или сессиям |
| `games` | игры библиотеки | отдельная сущность `Game` из ПР3 |
| `gamesessions` | игровые сессии | отдельная сущность `GameSession` из ПР3 |
| — | пользователи | в Django уже есть модель `User` (`django.contrib.auth`); работа с пользователями появится вместе с аутентификацией |

Приложение сессий названо `gamesessions`, а не `sessions`: метку
`sessions` уже занимает встроенное приложение `django.contrib.sessions`.

Приложения зарегистрированы в `INSTALLED_APPS` (`gamelibrary/settings.py`).
В настройках также заданы `LANGUAGE_CODE = "ru-RU"`,
`TIME_ZONE = "Europe/Moscow"` и `DATA_DIR = BASE_DIR / "data"` — каталог
JSON-файлов, из которого страницы загружают данные независимо от
каталога запуска сервера.

### Страницы и URL

| URL | View-функция | Страница |
|---|---|---|
| `/` | `homepage.views.index()` | описание приложения, сводка библиотеки, навигация |
| `/games/` | `games.views.games()` | список игр из `data/games.json` |
| `/games/<int:game_id>/` | `games.views.game_detail()` | карточка игры и прогресс игроков |
| `/sessions/` | `gamesessions.views.sessions()` | список сессий из `data/sessions.json` |
| `/sessions/<int:session_id>/` | `gamesessions.views.session_detail()` | карточка сессии со связанными игрой и игроком |

Если игра или сессия с указанным идентификатором не найдена, страница
возвращает сообщение об ошибке и код статуса **404**. Нечисловой
идентификатор (`/games/witcher/`) не проходит конвертер `int` и тоже
даёт 404.

Маршрутизация двухуровневая: `gamelibrary/urls.py` распределяет адреса
между приложениями функцией `include()`, а `urls.py` каждого приложения
описывает свои адреса. У всех маршрутов есть имена (`name=`), ссылки на
страницах строятся функцией `reverse()` по именам, а не жёстко заданными
адресами.

Путь запроса `/games/1/`:

```text
Браузер: GET /games/1/
  → gamelibrary/urls.py: path("games/", include("games.urls"))
  → games/urls.py:       path("<int:game_id>/", views.game_detail)
  → games.views.game_detail(request, game_id=1)
      load_library() → find_game_by_id() → game_progress()
  → HttpResponse: HTML-страница игры, 200 OK
```

| `game_detail()` | `games/views.py` | страница `/games/<id>/`; 404, если игры нет |
| `progress_html()` | `games/views.py` | шкала прогресса Bootstrap по объекту `Progress` |
| `sessions()` | `gamesessions/views.py` | страница `/sessions/`: сессии по датам с бейджами статуса |
| `session_detail()` | `gamesessions/views.py` | страница `/sessions/<id>/`; 404, если сессии нет |

Функция `page()` размещена в `homepage`, потому что главная страница
задаёт общий вид остальных страниц; приложения `games` и `gamesessions`
импортируют её. Формирование HTML в Python-строке — временное решение:
при переходе на шаблоны (`render()` и `base.html`) функция `page()`
будет заменена шаблоном.

View-функции не дублируют предметную логику. Они получают запрос,
загружают данные функциями ПР3, находят объект по идентификатору,
вызывают методы и функции модели и формируют HTML-ответ. Данные из
файлов (названия, жанры, имена) экранируются функцией
`django.utils.html.escape()`, поэтому попадают на страницу как текст,
а не как разметка.

### Функции ПР3 в веб-интерфейсе

| Функция ПР3 | Использование в ПР5 |
|---|---|
| `load_library()` (`load_games()`, `load_users()`, `load_sessions()`) | загрузка данных всеми страницами |
| `find_game_by_id()` | **новая**: страница игры, `None` → 404 |
| `find_session_by_id()` | **новая**: страница сессии, `None` → 404 |
| `find_user_by_id()` | **новая**, пока используется только через `get_user()` |
| `game_progress()`, `get_progress()`, свойства `Progress` | прогресс игроков на страницах игры и сессии |
| `active_sessions()`, `hours_played()` | активные сессии и сыгранные часы |
| `Game.era()`, `Game.rating_label()` | эпоха и описание оценки игры |
| `GameSession.is_cancelled` | бейдж «активна» / «отменена» |
| `library_stats()` | сводка на главной странице |
| `add_game()`, `remove_game()`, `find_games()`, `filter_games_by_*()`, `sort_games()` | отложены — нужны формы |
| `log_session()`, `cancel_session()` | отложены — нужны формы и POST-запросы |
| `add_user()`, `find_users()` | отложены — появятся вместе с аутентификацией |
| `show_*()` из `main.py` | не используются — вывод в консоль не для веба |

Функции `get_game()`, `get_user()` и `get_session()` теперь используют
новые `find_*_by_id()`: поиск написан один раз, а консольная версия
по-прежнему получает `KeyError` для несуществующего идентификатора.

- `manage.py` — запуск команд Django: `runserver`, `migrate`, `check`, `test`.

- `homepage/`, `games/`, `gamesessions/` — Django-приложения веб-интерфейса:

  обратно, восстановление связей сессий с пользователями и играми;
  `load_library()` загружает все три коллекции из каталога данных и
  используется и консольной, и веб-версией.
- `utils.py` — безопасный ввод строк, чисел, дат и выбора из списка.

## Формат хранения данных

Данные хранятся в каталоге `data/` в формате JSON. Чтение и запись выполняются в модуле `storage.py` через контекстный менеджер `with`; отсутствие файла даёт пустую коллекцию, а некорректный JSON или запись приводят к исключению `ValueError` с указанием файла и номера записи.

`data/games.json`:

```json
[
  {
    "id": 1,
    "title": "The Witcher 3: Wild Hunt",
    "genre": "RPG",
    "platform": "PC",
    "release_year": 2015,
    "hours_total": 100.0,
    "rating": 10
  }
]
```

`data/users.json`:

```json
[
  {
    "id": 1,
    "name": "Иван Петров",
    "email": "ivan@example.com"
  }
]
```

`data/sessions.json` — связи хранятся идентификаторами `user_id` и `game_id`:

```json
[
  {
    "id": 1,
    "user_id": 1,
    "game_id": 1,
    "date": "2026-09-10",
    "hours": 4.5,
    "is_cancelled": false
  }
]
```

Преобразование данных:

```text
При загрузке:   JSON → dict → Game.from_data() / User.from_data() → объект
                сессия: user_id, game_id → поиск User и Game → GameSession
При сохранении: объект → to_data() → dict → JSON
```

Сначала загружаются игры и пользователи, затем сессии: каждая сессия
получает ссылки на объекты из уже загруженных коллекций. Если пользователь
или игра сессии не найдены, сессия не создаётся и загрузка сообщает об
ошибке. Даты сессий хранятся в файле строками формата `ГГГГ-ММ-ДД` и
преобразуются в объекты `date`.

## Развитие проекта

- **ПР1** — сценарий для одной игры на отдельных переменных.
- **ПР2** — данные переведены в коллекции словарей, логика разбита на функции
  и модули, добавлены JSON-хранение, исключения и тесты.
- **ПР3** — функциональная модель переработана в объектную: игры, сессии и
  прогресс стали классами, добавлена сущность пользователя. Функции
  сценария ПР1 развиты в методы и свойства классов: `get_era()` и
  `get_rating_label()` — в методы `Game`, `calculate_progress()`,
  `get_status()` и `make_progress_bar()` — в свойства `Progress`.
- **ПР5** — к объектной модели добавлен веб-слой на Django: проект
  `gamelibrary`, приложения `homepage`, `games` и `gamesessions`,
  двухуровневая маршрутизация, view-функции и страницы с Bootstrap.
  Классы, JSON-хранилище, консольная версия и тесты ПР3 продолжают
  работать.

## Запуск тестов

Тесты предметной области и хранилища (ПР2–ПР3):

```text
pytest -v
```

Тесты веб-страниц (ПР5) запускаются средствами Django:

```text
python manage.py test
```

Тесты страниц используют `SimpleTestCase` (без базы данных) и временный
каталог с тестовой библиотекой, который подменяет `DATA_DIR`, поэтому не
зависят от содержимого `data/`. Они проверяют связь URL с view-функциями,
коды статуса 200 и 404, отображение данных и связанных объектов,
экранирование HTML, подключение Bootstrap и ссылки навигации.

Тесты `pytest` проверяют:

- создание объектов `Game`, `User`, `GameSession`, `Progress` и значения их атрибутов;
- строковое представление объектов;
- проверку данных в конструкторах и статических методах;
- поиск, отбор, сортировку и добавление объектов в коллекции;
- связь сессии с объектами пользователя и игры;
- правило одной активной сессии по игре за день и освобождение дня после отмены;
- личный прогресс и статусы прохождения;
- сохранение объектов в JSON и восстановление связей при загрузке;
- статистику библиотеки.

## Проверка качества кода

```text
flake8 .
```

Проверяются все Python-файлы проекта, включая созданные Django; каталоги
виртуального окружения (`.venv`, `venv`) исключены в `setup.cfg`.

Проверка типов:

```text
mypy .
```

Сам Django не содержит аннотаций типов, поэтому для mypy подключён пакет
`django-stubs` и его плагин (`setup.cfg`, раздел `[mypy]`). Без него mypy
сообщает `Skipping analyzing "django...": missing library stubs`.
View-функции аннотированы: `request: HttpRequest`, результат —
`HttpResponse`.
